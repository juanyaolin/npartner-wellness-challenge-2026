## 1. 專案定位

- 專案名稱：N-Partner 三比八大賽 2026
- 主要用途：公司內部 / intranet 使用的活動介紹與賽況展示網站
- 部署型態：靜態網站，目標可部署到 GitHub Pages
- 專案路徑：`/mnt/c/www/npartner-wellness-challenge-2026`
- 專案文件路徑：`/mnt/c/www/npartner-wellness-challenge-2026/docs/status-page-planning.md`
- 目前重要頁面：
  - `index.html`：首頁
  - `hahago.html`：HAHAGO 說明頁
  - `walking.html`：健走賽介紹頁
  - `health.html`：健康賽介紹頁
  - `status.html`：預計新增的單一賽況頁

### 1.1 專案目錄與維護原則

- `/mnt/c/www/npartner-wellness-challenge-2026` 是正式 GitHub Pages 專案目錄，原則上只保留最新 production 檔案。
- 版本化草稿、設計探索或非正式備份可放在 `/home/hermes/hahago-intro-page-sketches/00X` 這類草稿目錄，不要混入正式專案目錄。
- 靜態網站檔案結構應維持清楚分層：
  - HTML 頁面放在專案根目錄，例如 `index.html`、`walking.html`、`health.html`、`status.html`
  - CSS 放在 `assets/css/`
  - JavaScript 放在 `assets/js/`
  - 圖片與 QR code 等媒體放在 `images/`
  - CSV 或測試資料建議放在 `data/`
  - 專案規劃與備忘文件放在 `docs/`
- 交付前應執行可用的 formatter / linter / 檢查流程；若專案尚未配置工具，至少要檢查 HTML/CSS/JS 檔案結構、連結路徑與瀏覽器 console error。

## 2. 頁面導覽規劃

主頁與各項賽事頁都需要有可以跳轉到賽況頁的按鈕。

建議導覽：

```text
首頁 index.html
├─ 前往健走賽介紹 walking.html
├─ 前往健康賽介紹 health.html
└─ 查看賽況 status.html

健走賽介紹頁 walking.html
└─ 查看健走賽賽況 status.html?contest=walking

健康賽介紹頁 health.html
├─ 查看男子健康賽賽況 status.html?contest=health-men
└─ 查看女子健康賽賽況 status.html?contest=health-women

賽況頁 status.html
├─ Tab 1：健走賽
├─ Tab 2：男子健康賽
└─ Tab 3：女子健康賽
```

設計決定：

- 賽況頁只做一個頁面：`status.html`
- 不採用「健康賽 tab 裡再切男女」的巢狀 tab
- 直接用三個 top-level tabs 呈現三個賽事：
  - 健走賽
  - 男子健康賽
  - 女子健康賽
- 可用 URL query 指定預設開啟的賽事：
  - `status.html?contest=walking`
  - `status.html?contest=health-men`
  - `status.html?contest=health-women`

原則：

- 建議三個賽事拆成三份 CSV，避免不同賽事欄位混雜

建議資料檔：

## 5. 健走賽資料格式與規則

### 5.1 CSV 欄位

健走賽 CSV 預計提供：

- 參賽者編號
- 參賽者暱稱
- 週期編號
- 週期開始日期
- 週期結束日期
- 週期步數

原始資料型態概念：

```ts
type WalkingRawRow = {
  participantId: string;
  nickname: string;
  periodId: string;
  periodStartDate: string;
  periodEndDate: string;
  periodSteps: number;
};
```

正規化後資料型態概念：

```ts
type WalkingParticipant = {
  id: string;
  nickname: string;
  periods: {
    periodId: string;
    startDate: string;
    endDate: string;
    steps: number;
    cumulativeSteps: number;
  }[];
  totalSteps: number;
};
```

### 5.2 健走賽排名邏輯

- 以累計步數排名
- 缺少週期資料時，該週期視為 `0` 步
- 每個週期更新一次排名順序
- 長條圖依照累計步數排序
- 需要個人詳細資訊區域

### 5.3 步數攤分與無法整除問題

若需要把兩週期步數攤分到每日：

- 前面日期使用整數平均步數
- 最後一天補上剩餘差值
- 確保每日步數加總等於該週期步數

概念：

```js
const baseDailySteps = Math.floor(periodSteps / dayCount);
const remainder = periodSteps - baseDailySteps * dayCount;

// 前 dayCount - 1 天：baseDailySteps
// 最後一天：baseDailySteps + remainder
```

### 5.4 健走賽動畫

最新決定：

- 初版先不要播放 / 暫停 / 重播控制
- 頁面載入後自動依時間序列更新圖表
- 健走賽動畫速度先嘗試 `0.2 秒 / 天`
- 健走賽 CSV 仍由兩週期總步數提供，但前端需要先依「步數攤分與無法整除問題」規則把週期步數攤成每日資料，再用每日資料推進動畫
- 每天推進時要更新累計步數、排名與圖表；每個兩週期結束時，累計結果必須與 CSV 的週期步數加總一致
- 速度要設計成容易透過 code 更改

建議設定：

```js
const STATUS_ANIMATION = {
  walkingDayIntervalMs: 200,
  healthPeriodIntervalMs: 1000,
};
```

## 6. 健走賽圖表與個人詳細資訊

### 6.1 主要圖表

健走賽主圖：

- 動態累計步數長條圖
- 每天更新一次
- 名次變化時長條順序重新排序
- 名次變更動畫需要比目前純 DOM 寬度更新更流暢，最好呈現出「換位」的感覺，而不是瞬間跳到新順序
- 參賽者顏色保持一致

實作工具方向：

- 不需要自行用 DOM / SVG 從零繪製圖表
- 建議導入圖表工具處理主圖與線圖互動，優先考慮 Apache ECharts
- 選擇 Apache ECharts 的原因：
  - Apache 2.0 授權，較適合公司內部 / GitHub Pages 靜態網站使用，不需要先處理商業授權問題
  - 支援 bar chart、stacked bar、line chart、marker、tooltip、legend、click event
  - 可透過資料更新、排序與動畫設定實作較流暢的 bar race / 排名換位效果
- Highcharts.js 也可做到類似效果，但需注意商業 / 公司使用授權；除非後續確定有授權，否則先以 ECharts 為建議工具

### 6.2 個人詳細資訊區

選擇某位參賽者後，建議顯示。若使用 ECharts / Highcharts 等圖表工具，個人詳細資訊的選取應優先透過「直接點擊主圖上的參賽者資料列 / 資料點」觸發，不一定需要另外做一排獨立參賽者按鈕。

- 暱稱
- 目前排名
- 累計步數
- 本週期步數
- 平均每週期步數
- 最高單週期步數
- 與前一名差距
- 與下一名差距
- 歷週期步數圖表

## 7. 健康賽資料格式與規則

### 7.1 CSV 欄位

健康賽男女組共用同一種 CSV 格式，但資料來源分開：

- `health-men.csv`
- `health-women.csv`

CSV 預計提供：

- 參賽者編號
- 參賽者暱稱
- 週期編號
- 週期開始日期
- 週期結束日期
- 體重減少率
- 體脂肪減少率
- 骨骼肌增加率
- 累計體重減少率
- 累計體脂肪減少率
- 累計骨骼肌增加率
- 額外積分

重要決定：

- 健康賽的累計差值由 CSV 額外提供
- 程式不需要從每期變化率反推累積變化率
- 這樣可以避免百分比定義不一致造成誤差，也能節省計算邏輯

原始資料型態概念：

```ts
type HealthRawRow = {
  participantId: string;
  nickname: string;
  periodId: string;
  periodStartDate: string;
  periodEndDate: string;
  weightLossPercent: number;
  bodyFatLossPercent: number;
  skeletalMuscleGainPercent: number;
  cumulativeWeightLossPercent: number;
  cumulativeBodyFatLossPercent: number;
  cumulativeSkeletalMuscleGainPercent: number;
  extraPoints: number;
};
```

### 7.2 健康賽計分

CSV 不提供基本積分 / 排名積分。

程式需要計算：

- 加權健康百分比
- 每週期排名
- 每週期排名積分
- 每週期額外積分
- 每位參賽者累計總積分

目前活動規則中的加權公式：

```text
加權結果 = 體重減少率 * 30% + 體脂肪減少率 * 50% + 骨骼肌增加率 * 20%
```

建議用設定檔管理權重：

```js
const HEALTH_SCORE_CONFIG = {
  weightLossWeight: 0.3,
  bodyFatLossWeight: 0.5,
  skeletalMuscleGainWeight: 0.2,
};
```

排名積分規則依活動文件：

- 加權結果排名最後一名得 1 分
- 第一名得「參賽者人數」分
- 中間名次依序遞減

可由參賽者數量動態產生，例如 12 人：

```text
第 1 名：12 分
第 2 名：11 分
...
第 12 名：1 分
```

## 8. 健康賽圖表設計

每個健康賽 tab 內包含：

1. 積分長條圖
2. 加權百分比線圖
3. 個人詳細資訊區
4. 個人三項累計變化量線圖

### 8.1 積分長條圖

用途：呈現每位參賽者的積分狀態。

設計：

- 動態方式：每秒更新一個週期，即每秒跑過兩週
- 長條圖依照總積分重新排序
- 每個週期有兩種積分：
  - 排名積分
  - 額外積分
- 可用不同填滿樣式區分：
  - 排名積分：實心
  - 額外積分：斜線、點狀、半透明或不同紋理
- 同一參賽者在所有健康賽圖表中使用相同顏色
- 名次變更動畫需要盡可能流暢，呈現參賽者位置交換 / 排名換位效果；建議交由圖表工具的排序動畫或資料更新動畫處理
- 圖表上的參賽者資料列應可點擊，點擊後更新右側 / 下方個人詳細資訊區

### 8.2 加權百分比線圖

用途：呈現所有參賽者每個週期的加權健康百分比。

設計：

- 只畫加權後的百分比值
- 不同參賽者用不同顏色
- 同一參賽者顏色要與積分長條圖一致
- 每個節點都需要顯示 marker，讓觀看者可以清楚看出每個週期的資料點
- 線圖上的資料點可點擊時，應與個人詳細資訊區連動，顯示該參賽者資料
- 不要把體重、體脂肪、骨骼肌、額外積分等細項全部塞入這張總覽圖，以免太亂

### 8.3 個人詳細資訊區

選擇某位參賽者後，建議顯示。選取方式優先透過主圖或線圖 click event 觸發；獨立參賽者按鈕可以作為備援或手機版輔助，不是必要主互動。

- 暱稱
- 目前排名
- 目前總積分
- 排名積分累計
- 額外積分累計
- 本週期加權百分比
- 累計體重減少率
- 累計體脂肪減少率
- 累計骨骼肌增加率
- 歷週期積分明細

### 8.4 個人三項累計變化量線圖

個人詳細資訊區中另放一張線圖：

- X 軸：週期
- Y 軸：累計變化百分比
- 線 1：累計體重減少率
- 線 2：累計體脂肪減少率
- 線 3：累計骨骼肌增加率
- 每個週期節點都需要顯示 marker

資料直接使用 CSV 提供的累計欄位，不由程式反推。

## 9. 共用實作原則

### 9.1 資料處理流程

```text
Google Sheet CSV
        ↓
原始資料 parser
        ↓
資料正規化 / 補週期 / 補缺漏
        ↓
計算累計值、排名、積分、加權百分比
        ↓
圖表資料格式
        ↓
賽況頁 UI
```

### 9.2 圖表顏色

- 同一賽事中，同一參賽者顏色保持一致
- 健康賽中，同一參賽者在積分長條圖、加權百分比線圖、個人詳細資訊圖中顏色一致
- 男子健康賽與女子健康賽可各自產生色盤，不需要跨組保持同一 ID 顏色，除非資料上有跨組比較需求

### 9.2.1 圖表工具選擇

- 圖表不需要自行手刻 DOM / SVG，應導入成熟圖表工具
- 目前建議使用 Apache ECharts 作為賽況頁圖表工具
- 主要使用需求：
  - 健走賽累計步數 bar race / 排名換位動畫
  - 健康賽 stacked bar chart，排名積分與額外積分使用不同樣式
  - 健康賽加權百分比多參賽者 line chart
  - 個人三項累計變化量 line chart
  - 線圖 marker、tooltip、legend、click event
  - 點擊主圖資料列 / 資料點後，更新個人詳細資訊區
- 若改用 Highcharts.js，需先確認公司內部使用與 GitHub Pages 部署情境的授權是否符合需求

### 9.3 設定集中管理

建議將容易調整的規則集中到設定：

```js
const STATUS_CONFIG = {
  animation: {
    walkingDayIntervalMs: 200,
    healthPeriodIntervalMs: 1000,
  },
  healthScore: {
    weightLossWeight: 0.3,
    bodyFatLossWeight: 0.5,
    skeletalMuscleGainWeight: 0.2,
  },

```

### 9.4 暫不做的功能

初版暫不做：

- 播放 / 暫停 / 重播控制
- 複雜互動式時間軸
- 健康賽男女組內層 tab
- 從週期變化率反推健康賽累積變化率

未來可追加：

- 播放控制

- 更完整的參賽者比較功能

## 11. Google Sheet CSV 資料來源調整規劃

### 11.1 調整範圍與現況

- 三項賽事目前已在 `assets/js/status.js` 的 `STATUS_CONFIG.contests` 改用公開的 Google Sheet CSV 網址。
- `status.html` 本身沒有保存 CSV 網址；後續資料來源設定仍集中由 `assets/js/status.js` 管理。
- 本次後續開發應調整 CSV 欄位映射、有效紀錄判斷、健康賽量測資料模型、空資料處理及相關顯示文字。
- CSV 使用 Papa Parse 的 `header: true` 解析，因此實際取值依欄位名稱而非欄位位置；欄位順序改變不應影響取值，但仍應驗證必要欄位是否存在。
- 2026-06-20 檢查三份公開 CSV 時，所有現有紀錄的「是否有效」均不是「是」。這只是當下資料狀態，程式不可假設未來仍無有效資料。

```text
累計體脂肪減少率
累計骨骼肌增加率
```

調整重點：

- 新增「是否有效」欄位。
- 「週期編號」改為「量測編號」。
- 「週期開始日期」及「週期結束日期」移除，改為單一「量測日期」。
- 「額外積分」的位置提前；因程式依欄位名稱讀取，不應依欄位索引處理。
- 內部可保留供動畫使用的序列 ID，但命名應逐步由 `periodId` 改為 `measurementId`，避免資料語意混淆。
- 健康賽摘要不再顯示不存在的起訖日期，應改成顯示單一量測日期。
- 健康賽畫面中的「週期」文案應評估統一改為「量測」，例如「量測 1 / 12」。

### 11.3 「是否有效」判斷規則

「是否有效」是紀錄是否參與計算與顯示的唯一業務判斷來源：

```js
function isEffectiveRow(row) {
  return readText(row, "是否有效") === "是";
}
```

實作規則：

- 只有去除前後空白後完全等於「是」的紀錄才是有效紀錄。
- 「否」、空白、欄位缺失或其他文字一律視為「否」；預設值為「否」。
- 參賽者名單與週期／量測時間軸應先由 CSV 全部識別資料建立，再把「是否有效」套用到成績資料。
- 無效紀錄可用於辨識參賽者、暱稱、週期／量測編號與日期，但其步數、百分比及額外積分不得參與排名、積分與累計計算。
- 完全沒有有效成績的參賽者仍須保留在參賽者清單、圖表 series、圖例及個人詳細資訊中。
- 不再以步數、百分比、額外積分是否有值，或是否存在某一期輸入資料，推論紀錄是否有效。
- 參賽者編號及量測／週期編號仍是資料可被程式處理的必要識別欄位；缺少識別欄位屬於格式錯誤，不是另一套業務有效性規則。
- 若同一參賽者與同一週期／量測編號出現多筆紀錄，應依 CSV 列順序採用最後一筆作為目前狀態，再依該筆的「是否有效」決定是否計算。不可先過濾有效列再取最後一筆，否則較新的「否」無法撤銷舊的有效資料。
- 發現重複識別鍵時應在 console 輸出警告，方便追查 Sheet 堆疊或修正紀錄。

5. 健康賽排序改依量測編號的自然順序；若量測編號無法判斷先後，再以量測日期作為備援排序依據。

### 11.5 數值與公式錯誤處理

- Google Sheet 尚未完成計算的欄位可能出現空字串或 `#DIV/0!`。
- `readNumber()` 目前會把無法轉換的內容變成 `0`；後續應區分真正的數值 0、空值與公式錯誤，避免有效紀錄被靜默誤算。
- 「是否有效」為「否」的列可直接排除，不需檢查其公式結果。
- 「是否有效」為「是」但必要計算欄位仍有公式錯誤時，應輸出資料警告並採取明確策略。建議該筆不進入排名計算，且在頁面顯示資料異常提示；不可因此改判其他紀錄的有效性。
- 百分比欄位仍需支援純數字與帶 `%` 字元的字串。

### 11.6 無有效資料與錯誤狀態

當指定賽事沒有任何「是否有效 = 是」的紀錄時：

- 若已有日期到達的時間軸，仍可播放這些缺漏影格；若全部時間都在未來，才不啟動動畫計時器。
- 若 CSV 中仍有名單及已到達日期的時間軸資料，應顯示全部參賽者、空值圖表及「目前尚無有效成績」提示。
- 已到達日期但無效的健康賽紀錄仍顯示為當次量測 0 分；未來日期的無效預備列不顯示。
- 若 CSV 連名單或時間軸也不存在，才顯示整體空狀態。
- 不存取不存在的 `days[0]`、`periods[0]` 或參賽者成績資料。
- 此狀況應視為成功讀取但暫無可展示資料，與網路錯誤、CSV 解析失敗或必要表頭缺失分開呈現。
- 切換到其他賽事分頁時仍應正常重新載入或顯示快取資料。

### 11.7 驗證與測試清單

至少覆蓋以下情境：

- 「是否有效」為「是」的列會進入參賽者、排名、積分與圖表。
- 「否」、空白、欄位缺失及未知值均不進入任何計算。
- 無效列即使有完整數值也不會作為成績顯示，但其名單與時間軸識別資訊仍可使用。
- 有效列的數值為 0 時仍是有效紀錄。
- 完全沒有有效成績的參賽者仍會出現在圖表、圖例、參賽者按鈕與個人明細。
- 健走賽可正確讀取「周步數」，累計步數與每日拆分結果不受欄位順序影響。
- 健康賽可依「量測編號」排序，並在摘要及圖表顯示「量測日期」。
- 男子與女子健康賽使用相同新格式及有效性規則。
- 三份 CSV 全部沒有有效紀錄但仍有名單時，頁面顯示完整名單、空值圖表與提示，且 console 無未捕捉錯誤。
- 有效紀錄含空值、`#DIV/0!`、百分比字串、千分位逗號時，處理結果符合既定策略。
- CSV 缺少必要表頭時顯示明確錯誤。
- 同一參賽者同一量測／週期出現重複列時，以最後一列為準；最後一列為「否」時可撤銷舊的有效成績，並留下警告。
- URL 直接開啟 `?contest=walking`、`?contest=health-men`、`?contest=health-women` 均可正常顯示。

### 11.9 本機 CSV 範本與情境 fixture 策略

現有三份本機 CSV 保留為開發期間的基準範本：

- `data/walking.csv`：27 位參賽者、18 個週期
- `data/health-men.csv`：10 位參賽者、10 次量測
- `data/health-women.csv`：11 位參賽者、10 次量測

週期與量測次數不在本機自行假設，應以 Google Sheet 當下定義為準。2026-06-20 同步結果：

- 健走賽：18 週，2026/06/08 至 2026/10/11。
- 男子／女子健康賽：10 次量測，2026/06/08 至 2026/10/12。
- Google Sheet 中無週期／量測編號的空白預備列不納入本機 fixture。
- 若未來 Sheet 增減時間點，重新產生本機 fixture 前應先同步產生腳本中的時間軸。

後續執行時應先將三份基準範本同步成 Google Sheet 的新表頭：

- 健走賽加入「是否有效」，並將「週期步數」改為「周步數」。
- 健康賽加入「是否有效」，將週期欄位改為「量測日期／量測編號」，移除週期起訖日期。
- 基準範本預設設計成所有紀錄皆有效，可作為完整資料來源及衍生 fixture 的單一基準。
- 本機 CSV 是測試資料，不回寫 Google Sheet，也不改變正式環境預設資料來源。
- `scripts/generate-status-fixtures.ps1` 用於依固定公式重建三份基準資料，確保人數、時間點及累計數值可重現。

為了真正測試整份資料集的不同狀態，不應只在同一份 CSV 中各安排一位完整、部分缺漏及完全缺漏的參賽者。建議由三份基準範本衍生以下目錄：

```text
data/scenarios/
  complete/
    walking.csv
    health-men.csv
    health-women.csv
  partial-missing/
    walking.csv
    health-men.csv
    health-women.csv
  participant-missing/
    walking.csv
    health-men.csv
    health-women.csv
```

情境檔應由固定規則產生或維護，避免每次測試的人選與缺漏位置不同。若加入 fixture 產生腳本，三份根目錄 CSV 為來源，情境檔為可重建產物。

開發資料來源切換建議使用 URL query，避免修改正式設定才能測試：

```text
status.html?source=local&scenario=complete&contest=walking
status.html?source=local&scenario=partial-missing&contest=health-men
status.html?source=local&scenario=participant-missing&contest=health-women
```

規則：

- 未指定 `source=local` 時使用 Google Sheet。
- 指定本機來源但情境名稱不存在時顯示明確錯誤，不可靜默回退或載入其他資料。
- 快取鍵需包含資料來源與情境，避免切換情境後沿用上一份資料。
- 頁面可在摘要區標示「本機測試資料」，避免誤認為正式賽況。

### 11.10 三組必要模擬情境

下列三組情境必須同時涵蓋健走、男子健康與女子健康三項賽事。

#### 情境 A：所有參賽者都有資料

- 每位參賽者在每個週期／量測都有一列資料。
- 所有列的「是否有效」皆為「是」。
- 包含至少一筆有效數值為 `0` 的資料，以確認 0 不會被誤判為無效。
- 用途：驗證正常動畫、完整排名、累計、圖表、明細及最後結果。

#### 情境 B：少數參賽者在部分時間沒有資料

- 固定挑選至少 2 位參賽者。
- 一位缺少前段資料，一位缺少中段或後段資料，避免只驗證單一缺漏型態。
- 缺漏以該列「是否有效 = 否」表示；列仍保留名單、編號與日期骨架。
- 健走賽缺漏週期不增加步數，之後有資料時從先前累計值繼續。
- 健康賽中，日期已到達但無效的量測紀錄為當次積分 0 分，不取得排名積分或額外積分；加權折線以 `null` 形成中斷，不可把身體數據補成 0。
- 用途：驗證不連續資料、折線缺口、累計延續、當期未排名狀態及動畫穩定性。

#### 情境 C：少數參賽者完全沒有資料

- 固定挑選至少 2 位參賽者，將其所有列設為「是否有效 = 否」。
- 參賽者仍須出現在：
  - 參賽者切換按鈕
  - 排名圖的參賽者列
  - 健康賽圖例與 series
  - 個人詳細資訊
- 這些參賽者顯示「尚無有效資料」，不可顯示為最後一名，也不可取得排名積分。
- 健走賽的目前累計可顯示 0，但必須搭配「尚無資料」狀態，避免與有效的 0 步混淆。
- 健康賽積分圖保留 0 值參賽者列並使用弱化樣式；折線 series 保留但所有節點為 `null`。
- 用途：驗證名單與成績分離，以及零長條／無節點 series 不會造成點擊與明細錯誤。

### 11.11 缺漏資料的排名與顯示規則

- 名單人數以 CSV 中可辨識的參賽者編號為準，不以有效成績列數為準。
- 各期排名只排列當期有有效成績的參賽者；沒有當期成績者顯示「未排名」。
- 健康賽排名積分級距維持以完整參賽名單人數計算；沒有當期有效資料者得 0 分，其餘有效參賽者依名次取得積分。
- 健走賽缺少某週資料時，該週新增步數為 0，但參賽者過去的累計步數仍保留。畫面需區分「本週無資料」與「本週有效 0 步」。
- 健康賽缺少某次量測時：
  - 本期百分比、加權結果與名次為 `null`
  - 本期排名積分與額外積分為 0
  - 本期總積分增加值為 0，畫面明確顯示「未量測／未提供資料，當期 0 分」
  - 過去累計總積分延續
  - 身體數據折線不自行補值，該次量測顯示缺口
- 圖表排序時，有當期有效資料者優先；無當期資料者排在後方，彼此依參賽者編號或暱稱穩定排序。
- 個人明細需顯示資料狀態，例如「有效資料」、「本期未提供資料」或「尚無任何有效資料」。

### 11.12 建議補充的穩定性情境

除三組主要情境外，至少再驗證：

- 全賽事尚無任何有效成績，但已有完整參賽名單及時間軸。
- 第一個週期／量測全部無資料，後續才開始有資料。
- 最後一個週期／量測日期已到但全部無資料時仍須渲染；若日期尚未到達則完全不渲染。
- 同一參賽者同一期出現重複有效列。
- 有效列包含空值、`#DIV/0!`、非數字、負數、極大值或帶 `%` 的文字。
- 參賽者暱稱重複，但參賽者編號不同。
- 同一參賽者在不同列出現不同暱稱；建議採最後一個非空暱稱並輸出警告。
- 週期／量測編號順序混亂、缺號或日期不按 CSV 列順序排列。
- CSV 只有表頭、缺少必要表頭、含空白列或額外未知欄位。
- 網路讀取失敗、Google Sheet 回傳非 CSV 內容，以及本機 fixture 路徑不存在。

### 11.14 Google Sheet 持續堆疊與逐步生效

Google Sheet 的資料生命週期不是一次性匯入，而是：

1. 先建立參賽者與未來週期／量測的預備列。
2. 預備列預設「是否有效 = 否」，數值可能為空白或公式錯誤。
3. 隨活動進行，既有列可能改成「是」，也可能在表尾追加新的紀錄或修正列。

程式需遵守以下規則，避免尚未公布的資料造成錯誤：

- 所有列可用於建立完整參賽者名單。
- 每次開啟頁面時取得的 CSV 視為該次瀏覽工作階段的最新資料快照。
- 正式賽況的「目前進度」由日期是否已到達決定，不由「是否有效」決定，也不直接採用 CSV 最後一列或最大編號。
- 日期在今日或過去且標記為「否」的列，代表參賽者該次未提供資料或未量測，必須渲染為缺漏狀態。
- 健康賽的過去／今日無效量測，當期積分明確記為 0 分，但不產生虛假的百分比、加權值或排名。
- 日期在未來且標記為「否」的列是尚未到期的預備資料，不建立動畫影格、不顯示進度、不渲染圖表節點，也不參與任何計算。
- 若所有已到達日期的紀錄均為「否」，仍保留完整名單及已到達的時間軸，顯示缺漏狀態；只有全部紀錄都在未來時才顯示「賽事尚未開始」。
- 當第一筆資料由「否」變為「是」時，頁面重新載入資料後應能正常建立第一個影格、排名及個人明細。
- 新週期／量測開始生效時，動畫與摘要需自然擴充，不可依初次載入時的固定期數。
- 已有效的紀錄後來改回「否」時，重新整理後必須從計算中移除，並重新計算後續累計、排名與積分。

#### 時間軸分層

資料模型應區分：

- `knownTimeline`：CSV 中可辨識的所有週期／量測，包含未來預備資料，可供名單骨架及資料檢查使用。
- `visibleTimeline`：日期在今日或過去的週期／量測，正式動畫、圖表及目前進度只使用此集合。

判定方式：

- 健康賽以「量測日期」判斷：`量測日期 <= 今日` 才進入 `visibleTimeline`。
- 健走賽以週期日期判斷：
  - `週期開始日期 > 今日`：整個週期不渲染。
  - `週期開始日期 <= 今日 <= 週期結束日期`：只渲染到今日，不產生未來日期的每日影格。
  - `週期結束日期 < 今日`：渲染完整週期。
- 日期比較以活動使用時區 `Asia/Taipei` 的日曆日期為準，忽略時、分、秒，避免使用者裝置時區造成提前或延後一天。
- `visibleTimeline` 依日期及編號排序，不依 CSV 列出現順序。
- 某個已到達的時間點即使所有參賽者均為「否」，仍保留影格並顯示「本期無人提供資料」。
- 未來預備資料一律留在 `knownTimeline`，不進入正式畫面。

#### 重新讀取與快取

本階段採用「每次開頁取得最新快照」，不要求頁面開啟期間即時輪詢。後續需調整：

- 每次重新開啟或重新整理網頁時重新抓取 Google Sheet CSV。
- 正式 Google Sheet 模式的 `fetch` 使用 `cache: "no-store"`，降低瀏覽器或中介快取讀到前一次頁面資料的機率。
- 同一次頁面工作階段內可保留各賽事的記憶體快取，切換分頁不必重複下載。
- 本階段不實作定時自動更新；若使用者需要新資料，重新整理頁面即可取得下一份最新快照。
- 本機 fixture 可維持穩定快取，不需要套用正式 Sheet 的自動更新策略。
- 初次載入失敗時顯示讀取錯誤；同一工作階段內若未來加入手動重抓功能，失敗時才保留上一份成功資料。

#### 資料版本與競態保護

- 使用請求序號或 `AbortController`，避免使用者快速切換賽事時，較早發出的慢請求覆蓋目前賽事。
- 每次成功解析後再一次性替換快取，不可在正規化到一半時改寫目前畫面狀態。
- 若更新後參賽者或目前影格仍存在，保留使用者目前選取狀態；不存在時才安全回退到第一位參賽者或 `visibleTimeline` 的最後一個影格。

#### 追加驗收情境

- 初始所有列均為「否」，之後第一筆改為「是」。
- 關閉或重新整理頁面後，讀取下一期新增的最新資料。
- 預先存在多個未來「否」的週期，但目前進度只到今日已到達的週期。
- 過去／今日的整期資料全部為「否」時仍渲染該期，健康賽所有人當期皆為 0 分。
- 健走賽目前週期尚未結束時，只產生到今日為止的每日影格。
- 明日日期的無效量測在今日不可見，日期到達後重新開頁則顯示為未量測、當期 0 分。
- 新增重複鍵的修正列，最後一列「是」覆蓋舊值。
- 新增重複鍵的撤銷列，最後一列「否」移除舊成績。
- 更新後參賽者名單增加、暱稱改變或量測期數增加。
- 更新請求失敗時仍保留上一份成功畫面。
- 快速切換三個賽事時，慢速舊請求不會覆蓋目前分頁。

## 12. 長賽程預覽與健走動畫調整規劃

### 12.1 本機模式指定模擬日期

目前正式與本機模式皆以 `Asia/Taipei` 的實際日期判斷可見時間軸。由於目前日期接近開賽時間，本機測試只能看到前段資料，不足以驗證中段缺漏、後段累計與完整賽程圖表。

後續在本機模式加入 `asOf` query parameter，作為「模擬今日」：

```text
status.html?source=local&scenario=partial-missing&contest=walking&asOf=2026-08-31
status.html?source=local&scenario=partial-missing&contest=health-men&asOf=2026-09-28
```

規則：

- 只有 `source=local` 時允許使用 `asOf`。
- 正式 Google Sheet 模式一律忽略 `asOf`，避免使用者修改網址後看到未來資料。
- `asOf` 僅接受 `YYYY-MM-DD` 格式，解析後轉成目前程式使用的日期鍵。
- 日期不存在或格式錯誤時顯示明確錯誤，不靜默採用其他日期。
- `asOf` 必須落在該賽事已知時間軸範圍內；超出範圍時顯示可用日期區間。
- 日期判斷仍以 `Asia/Taipei` 日曆日期為準。
- 本機測試資料標記需追加顯示模擬日期，例如：

```text
本機測試資料｜partial-missing｜模擬日期 2026/08/31
```

### 12.2 長賽程快速入口

`status-scenarios.html` 除了目前九個「實際今日」連結，再為每個情境提供以下日期入口：

- 賽程前段：2026-06-20
- 賽程中段：2026-08-31
- 賽程後段：
  - 健走賽：2026-10-11
  - 健康賽：2026-10-12

建議介面：

- 每個情境卡片保留三項賽事按鈕。
- 增加「今日／中段／完整賽程」日期選擇區，避免直接排列大量難以辨識的連結。
- 點擊後產生包含 `source`、`scenario`、`contest`、`asOf` 的完整 query。
- 頁面附上目前情境缺漏位置說明，方便直接跳到可觀察缺漏的日期。

情境 B `partial-missing` 目前固定缺漏：

- 參賽者 1：第 1、2 個週期／量測無資料。
- 參賽者 2：第 5、8 個週期／量測無資料。

因此中段與後段入口必須至少能檢查：

- 前段無資料後，後續恢復提供資料時累計是否正確。
- 第 5 期缺漏當下的圖表、排名與明細。
- 第 8 期再次缺漏時，先前累計是否延續。
- 健康賽折線在缺漏位置是否保留 `null` 缺口。
- 健走賽缺漏週期是否新增 0 步，但過去累計仍保留。

### 12.3 健走動畫改為子影格

目前健走動畫每個日資料影格間隔為 200ms。後續改成「每日資料點不變、日內增加動畫子影格」：

```js
walkingAnimation: {
  framesPerDay: 10,
  frameIntervalMs: 30,
}
```

建議初始值：

- 每日 10 個子影格。
- 每個子影格間隔 30ms。
- 每日約 300ms 播放完成，數值更新頻率由每日一次提高為每日十次。
- 雖然單日播放時間比原本的 200ms 稍長，但畫面會有更頻繁、連續的數值與排名變化。
- 設定集中管理，日後可只修改參數，不需改計算邏輯。

### 12.4 子影格數值分配規則

CSV 只提供每週總步數，因此動畫中的每日及 tick 數值皆為視覺模擬資料。後續改成直接將每週步數分配到該週的所有 tick：

1. 完整一週建立 `7 × 10 = 70` 個 tick。
2. 為每位參賽者、每個週期及每個 tick 產生不同的隨機權重。
3. 依權重比例分配該週總步數。
4. 使用整數配額及最大餘數法修正，確保所有 tick 加總後完全等於 CSV 的「周步數」。
5. 進行中的週期只播放到模擬日期／實際今日所包含的 tick，但完整 70 tick 的分配結果保持不變。

概念範例，某週共有 10,003 步、簡化為 4 個 tick，隨機權重為：

```text
權重：0.8、1.4、0.5、1.1
初步分配：2,106、3,685、1,316、2,895
餘數修正後：所有 tick 加總必須為 10,003
```

精確性要求：

- 每日最後一個 tick 的累計值即為該日模擬結果；每日步數不再要求平均或固定。
- 每週最後一個子影格的累計增量必須完全等於 CSV 的「周步數」。
- 多週累計不得因除法或浮點數產生誤差。
- 所有步數增量使用整數。
- 無效週期的所有子影格增量皆為 0，並保持「本週未提供資料」狀態。
- 進行中的當週只建立到模擬日期／實際今日，不建立未來日期及其子影格。

### 12.4.1 可重現的隨機分配

隨機結果不可使用每次呼叫都不同的 `Math.random()`，否則重新整理後排名動畫會改變，難以測試與重現問題。

建議使用 seeded pseudo-random generator：

```text
seed = 參賽者編號 + 週期編號 + 固定動畫版本字串
```

規則：

- 同一份 CSV、同一參賽者及同一週期每次載入都得到相同 tick 序列。
- 不同參賽者使用不同 seed，避免所有人的高峰同時發生。
- 調整演算法時更新動畫版本字串，讓新舊分配結果可以明確區分。
- 本機 fixture 與正式 Google Sheet 使用相同分配演算法。
- 「是否有效 = 否」的週期不執行隨機分配，所有 tick 固定為 0。

### 12.4.2 增加排名變動的權重模型

單純在平均值附近小幅隨機，可能無法明顯影響 27 人的排名順序。權重需同時包含：

- 基礎活動量：確保每個 tick 大多仍有合理增量。
- 個人高峰時段：每位參賽者在不同日或不同 tick 出現 1 至 3 段較高權重。
- 短暫低活動時段：部分 tick 使用較低權重，形成追趕空間。
- 少量 burst：少數 tick 可有明顯較大的增量，讓長條排名出現可見交換。

建議權重範圍：

```text
一般 tick：0.45 ～ 1.35
低活動 tick：0.10 ～ 0.40
高峰 tick：1.60 ～ 2.80
```

限制：

- 權重不得為負數。
- 不應讓單一 tick 取得過高比例的週步數；建議單 tick 上限不超過該週總步數的 8%。
- 每位參賽者的高峰位置需不同，否則排名仍會同步移動。
- 隨機效果只改變步數何時出現，不改變每週及完整賽程最終數值。
- 週步數差距極大時不保證一定交換排名；不可為了製造交換而竄改週總數。

### 12.5 動畫與畫面更新

新增子影格後：

- 圖表長條及累計數字每個子影格更新一次。

- 「本週期累計」同步顯示截至目前子影格的累計值。

## 13. 健走排名交換過渡動畫規劃

### 13.1 現況與原因

目前排名順序雖然會隨 tick 改變，但圖形直接出現在新位置，主要原因不只是 30ms tick 太密，而是健走圖表目前明確關閉動畫：

```js
animation: false,
animationDuration: 0,
animationDurationUpdate: 0,
```

另外目前使用：

```js
chart.setOption(option, true);
```

第二個參數 `true` 代表 `notMerge`，每次更新都以接近重建圖表設定的方式處理。即使重新開啟動畫，也可能因分類軸及資料列被整批替換，無法穩定辨識同一位參賽者從舊排名移動到新排名。

因此後續需要同時處理：

- 重新啟用 ECharts 更新動畫。
- 保持每位參賽者資料項目的穩定識別。
- 避免每 30ms 中斷尚未完成的排名位移動畫。
- 將「資料計算 tick」與「圖表視覺更新」拆成不同頻率。

### 13.2 建議架構：資料 tick 與視覺快照分離

保留現有資料模型：

```text
資料 tick：每 30ms
每日 tick：10 次
```

新增較慢的圖表視覺快照：

```js
walkingAnimation: {
  framesPerDay: 10,
  frameIntervalMs: 30,
  chartUpdateEveryTicks: 4,
  chartTransitionMs: 110,
}
```

建議初始值：

- 累計步數、日期、排名及個人明細仍每 30ms 推進。
- 主排名圖每 4 個 tick 更新一次，即約每 120ms 更新。
- 排名位移動畫約 110ms，能在下一次圖表更新前大致完成。
- 每日 10 tick 約會產生 3 次主圖更新，日終強制更新一次。
- 每週最後一個 tick 也強制更新，確保週結算圖形與 CSV 數值完全一致。

這種做法會合併過密的中間圖形狀態，但不會略過任何資料計算。圖表呈現的是最新已計算快照，不會改變最終排名或步數。

### 13.3 ECharts 資料識別與更新方式

健走長條資料需要為每位參賽者提供穩定識別：

```js
{
  id: participant.id,
  name: participant.nickname,
  value: participant.current.cumulativeSteps,
}
```

調整原則：

- `series` 本身使用固定 `id`，例如 `walking-ranking-series`。
- 每個 data item 使用固定參賽者 `id` 及 `name`。
- 不再使用 `chart.setOption(option, true)` 完整重建。
- 改用合併更新，讓 ECharts 能追蹤同一 data item 的舊位置與新位置。
- 保留 `realtimeSort: true`，交由 ECharts 處理長條排序位移。
- 分類軸資料不應每次依前端排名結果整批重排；應維持穩定參賽者名稱集合，排名順序由 `realtimeSort` 控制。
- 若 ECharts 原生 `realtimeSort` 在 27 人時仍不穩定，再評估改用固定 data item 與 `universalTransition`，但不建議兩套排序動畫同時啟用。

### 13.5 更新排程與補幀


## 15. 缺漏週期／量測的累計排名修正規劃

### 15.1 問題說明

目前三項賽事的排序邏輯會優先判斷「目前週期／量測是否有效」：

```text
當期有資料者
  排在
當期無資料者
  前面
```

因此參賽者即使過去已有有效成績，只要目前週期或量測標記為「否」，就會暫時掉到所有有效資料者之後；下一次恢復有效資料時又突然回到原本累計排名。

這不符合累計型賽事的排名語意。當期缺漏只代表：

- 健走賽：本週不增加步數。
- 健康賽：本次量測取得 0 分。

它不應撤銷參賽者過去已累積的步數或積分，也不應暫停其排名資格。

### 15.2 正確排名資格

每個動畫時間點需要區分三種狀態：

1. `hasCurrentData`
   - 目前週期／量測有有效資料。
2. `hasValidDataToDate`
   - 從賽事開始到目前時間點，至少曾出現一筆有效資料。
3. `hasAnyKnownValidData`
   - 整份 CSV 中包含至少一筆有效資料，可能位於目前時間點之後。

排名必須使用 `hasValidDataToDate`，不可使用 `hasCurrentData` 或包含未來資料的 `hasAnyKnownValidData`。

規則：

- `hasValidDataToDate = true`
  - 正常參與累計排名。
  - 當期無效時累計值不增加，但名次仍依目前累計值決定。
- `hasValidDataToDate = false`
  - 排在所有曾有有效資料的參賽者之後。
  - 多位參賽者皆無任何有效資料時，依參賽者編號穩定排序。
- 未來日期才會有效的資料，不可讓參賽者提前取得排名資格。
- 一旦第一筆有效資料到達，該參賽者從該時間點開始正常加入排名。

### 15.3 健走賽調整

每個健走 tick 需保存：

```js
{
  hasCurrentData,
  hasValidDataToDate,
  cumulativeSteps,
}
```

累計方式：

- 有效週期：依 tick 分配增加步數。
- 無效週期：tick 增量為 0，沿用上一個 tick 的 `cumulativeSteps`。
- 過去曾有有效週期者，即使本週無效，仍以沿用後的 `cumulativeSteps` 正常排名。
- 截至目前從未有有效週期者，維持在排名底部。

排序順序：

```text
1. hasValidDataToDate：true 優先
2. cumulativeSteps：由高到低
3. 參賽者編號：自然排序
```

不再使用 `current.hasData` 作為第一排序條件。

範例：

```text
A：過去累計 100,000 步，本週無效
B：目前累計 90,000 步，本週有效
C：截至目前從未有有效資料

正確排名：
1. A
2. B
3. C
```

### 15.4 健康賽調整

每次量測資料需保存：

```js
{
  hasCurrentData,
  hasValidDataToDate,
  totalPoints,
}
```

累計方式：

- 有效量測：正常取得當期排名積分及額外積分。
- 無效量測：當期增加 0 分，沿用先前 `totalPoints`。
- 過去曾有有效量測者，即使本次無效，仍依累計總積分正常排名。
- 截至目前從未有有效量測者，排在所有已有有效紀錄者之後。

健康賽總排名排序：

```text
1. hasValidDataToDate：true 優先
2. totalPoints：由高到低
3. 最近一次有效量測的 weightedPercent：由高到低
4. 參賽者編號：自然排序
```

使用「最近一次有效量測的加權結果」作為同分次排序，可避免本期缺漏者因 `weightedPercent = null` 被不合理地排到同分者最後。

若尚無任何有效量測：

- `latestValidWeightedPercent = null`
- 排在已有有效資料者之後。
- 與其他完全無資料者依參賽者編號排序。

## 17. 健康賽第二期起算與同排名同分調整規劃

本節原為待確認後執行的調整規劃；目前已完成實作與驗證。

### 17.1 問題與目標

目前 `status.html` 的男子健康賽與女子健康賽都會從第一期量測開始計算積分。實際規則應為：

- 第一期量測是初始值／基準值，不計入健康賽積分。
- 第二期量測開始才是增減值，才開始計算排名積分與額外積分。
- 同一量測期中若加權結果相同，參賽者應取得相同名次與相同排名積分。
- 平手後的下一個名次採「下一個排名群」計算，不跳號。
- 因平手造成最後一名高於 1 分可以接受。

範例：總共 10 人時，若有兩人同為第二名，兩人都得 9 分；下一個排名群是第三名，得 8 分。

### 17.2 影響範圍

主要影響 `assets/js/status.js` 的健康賽資料正規化與排名計算：

- `normalizeHealth()`
  - 第一個健康賽量測影格需標記為基準期。
  - 基準期保留畫面顯示與身體數據，但不累加任何積分。
  - 第二期起才建立排名、排名積分與額外積分。
- 健康賽排名資料結構
  - 目前以排序後的 index 直接產生 `rank` 與 `rankingPoints`。
  - 需改為依加權結果分組，讓同分者共享同一個 dense rank。
- 健康賽排序與明細顯示
  - 第一期間總積分應為 0。
  - 第一期不應用基準值加權結果作為積分排名或總積分相同時的有效排名依據。
  - 明細狀態需能表達「基準量測，不計分」。

不影響健走賽計算。

### 17.3 第一期間不計分規則

健康賽時間軸仍沿用 `collectHealthTimeline()` 排序後的量測順序：

- 排序後第一筆量測視為 baseline measurement。
- `visibleFrames` 仍包含第一筆量測，讓畫面可以播放與顯示初始資料。
- 第一筆量測若有有效資料：
  - `hasData` 仍為 `true`。
  - 身體數據、累計身體數據與加權百分比仍可供畫面呈現。
  - `rankingPoints` 必須是 `0`。
  - `extraPoints` 必須是 `0`，即使 CSV 第一期間的「額外積分」有值也不計入。
  - `totalPoints`、`rankingPointsTotal`、`extraPointsTotal` 都維持 `0`。
  - `rank` 建議為 `null`，避免畫面誤認第一期已有積分排名。
- 第二筆量測起才進入計分：
  - 依當期有效資料計算加權結果。
  - 依當期加權結果產生排名與排名積分。
  - 讀取當期「額外積分」並累加。
  - 後續累計積分從第二期開始往後加總。

建議在量測 frame 上加入語意欄位：

```js
{
  measurementIndex,
  isBaselineMeasurement,
  isScoringMeasurement,
}
```

或至少在 `normalizeHealth()` 內用 index 控制計分流程，避免只靠 `measurementId === "1"`，讓未來量測編號格式變動時仍可依排序後第一期判斷。

### 17.4 同排名同分規則

目前 `calculateRankingPoints(rankIndex, participantCount)` 使用排序 index 計算分數，因此即使加權結果相同，後排序的人也會少一分。需改成「依分數群組」計算：

1. 先取出當期有效資料參賽者。
2. 依 `weightedPercent` 由大到小排序。
3. 加權結果相同者歸為同一個排名群。
4. 第一個排名群是第 1 名，第二個排名群是第 2 名，依此類推。
5. 排名積分用完整參賽者人數減去 dense rank 位移：

```text
rankingPoints = participantCount - (denseRank - 1)
```

若總人數是 10：

```text
第 1 名：10 分
第 2 名：9 分
第 2 名：9 分
第 3 名：8 分
```

同排名群內仍需要穩定排序，建議使用暱稱或參賽者編號作為畫面排序輔助，但不得影響 `rank` 與 `rankingPoints`。

### 17.5 浮點數與平手判斷

加權結果由三個百分比乘上權重後相加，可能出現 JavaScript 浮點誤差。平手判斷不可直接依字串或畫面格式，建議採其中一種策略：

- 建立 `normalizeWeightedScore(value)`，例如固定到 10 位小數後再比較。
- 或建立 `isSameWeightedScore(a, b)`，使用很小的 epsilon 判斷。

此判斷只用於排名分組；畫面顯示仍可沿用既有 `formatDecimal()`。

#### 18.7.2 健走資料模型與動畫窗口

- 保留 7 天 `knownTimeline` 作為 CSV 資料粒度，再建立每兩週一組的 `competitionPeriods`。
- 每個公開競賽期次保存兩筆健走週資料、14 天 tick、期初累計與期末累計。
- 歷史公開期次先計入累計底座；只把最新公開期次的 14 天 tick 交給排名動畫。
- 若同一次載入有多個新批次同時符合公開條件，只播放最新公開期次；更早的批次直接併入期初累計與歷史線圖。
- 第一個 tick 的長條值必須等於前一公開期次的期末累計，最後一個 tick 必須等於所有公開健走週資料的總和。

#### 18.7.3 健走每週步數線圖

- 將 walking 左側改用既有 `.status-main-column`，在排名圖下方加入第二個 `.line-chart` 容器。
- 每位參賽者使用與排名圖相同的固定顏色、marker、scroll legend 及點擊選取互動。
- 歷史週資料點在動畫開始時完整顯示；最新期次第一、二週的資料點只在各自週末最後一個 tick 後加入。
- 無效、空白或缺列的週資料在批次公開後畫為 0。
- X 軸顯示週次，tooltip 顯示暱稱、步數及完整日期範圍。

#### 18.7.4 健康賽

- 第一筆基準量測維持賽事開始日即可公開且不計分。
- 後續每筆量測視為剛結束競賽期次的資料；套用共用公開窗口與強制結算規則後，才加入既有積分動畫與線圖。
- 健康賽既有的基準期、dense rank、積分累計、加權百分比缺值與圖表樣式不另行改動。

#### 18.7.5 靜態頁限制

- 不新增 Sheet 欄位、後端、localStorage、輪詢、發布歷史或第三方相依套件。
- 每次載入重新抓取 Google CSV 並重算批次狀態；公開窗口內資料更新後，使用者需自行重新整理。
- 資料維護流程保證批次全數有效後不會在強制結算日前改回部分無效。

### 18.10 驗收項目

- 健走兩個相鄰 7 天週資料正確組成一個 14 天競賽期次；異常時間軸會顯示錯誤。
- 公開日前即使資料全數有效也不顯示；公開日後全數有效才整批顯示。
- 公開窗口內只要有任一預期資料無效、空白、缺列或必要數值不完整，三項賽事都維持上一批且不洩露個人狀態。
- 強制結算日會把仍未有效的資料按 0 納入，且不再阻擋整批公開。
- 最後一期可在正常公開日後繼續測到推算出的強制結算日。
- 健康賽第一筆基準量測仍在賽事開始日顯示且不計分。
- 健走排名動畫只播放最新公開的 14 天，第一個值承接前一期，最終累計與所有公開週步數總和一致。
- 健走線圖保留所有歷史週資料；最新兩點只在第 7、14 天最後一個 tick 後出現。
- 健走線圖缺漏資料顯示 0，週次、日期、顏色、legend、tooltip 與點擊選取正確。
- 退賽者從 CSV 移除全部資料後，不出現在名單、歷史圖表或完整性判斷中。
- 待彙整與首期進行中提示不包含任何個別參賽者狀態。
- 桌面與窄螢幕版面均可讀，瀏覽器 console 無錯誤。
- `npm run lint` 與 `git diff --check` 通過。
